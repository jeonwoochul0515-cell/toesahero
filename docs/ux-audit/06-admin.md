# 06 · 관리자 화면 점검 (접수함·상세·칸반·주문·통계·로그인)

법률사무소 실무자(비개발자)가 아침에 출근해 관리자 화면을 열고, 전화를 받고, 변호사에게 보고하는
하루를 따라가며 코드를 끝까지 추적했다. 화면에 실제로 그려지는 글자와 버튼이 무엇을 하는지만 근거로 삼았다.

## 발견

### 1. 화면의 합계 숫자가 실제 총계가 아니다 (최근 몇 건만 세고 "전체"라고 부른다) · 심각도 위험

- **어디서** 대시보드 상단 숫자 5개, 접수함 "N건", 결제 주문 "결제완료 합계".
- **무슨 일이** 조회가 최근 문서 몇 건만 가져오도록 제한되어 있는데, 화면은 그 안에서 센 값을
  "전체"·"합계"로 적는다. 대시보드는 200건, 칸반 300건, 접수함 500건, 주문 300건이 상한이다.
  접수가 쌓여 상한을 넘는 날부터 "전체 상담 요청"은 계속 200 부근에서 멈추고, 변호사에게 보고하는
  매출 합계도 최근 300건 밖의 결제를 빼고 계산된다. 화면 어디에도 "잘렸다"는 표시가 없다.
- **근거** `src/admin/AdminDashboard.tsx:23`(`watchConsultations(setRows, 200)`),
  `AdminDashboard.tsx:50`(`total: grouped.length`), `AdminDashboard.tsx:60`(라벨 "전체 상담 요청"),
  `src/admin/ConsultationsList.tsx:93`(500), `src/admin/Kanban.tsx:41`(300),
  `src/admin/OrdersAdmin.tsx:36`(300), `OrdersAdmin.tsx:67-73`(`paidTotal`은 받아온 rows만 합산),
  `src/firebase.ts:302-321`(`limit(max)`).
- **고칠 방향** 합계는 화면에서 세지 말고 집계값을 따로 두거나, 최소한 상한에 닿으면
  "최근 200건 기준"이라고 숫자 옆에 밝힌다. 매출 합계는 기간을 골라 서버에서 집계하는 편이 안전하다.

### 2. 오래된 사건을 열면 영원히 "로드 중..."에서 멈춘다 · 심각도 막힘

- **어디서** 상담 상세(`/admin/consultations/{id}`), 통보문 인쇄 화면.
- **무슨 일이** 상세 화면은 그 사건 하나를 불러오는 게 아니라 **최근 500건을 통째로 받아 그 안에서 id를 찾는다.**
  500건 밖으로 밀려난 사건은 목록에서 링크를 눌러도 화면이 "로드 중... (없는 ID 일 수도 있음)"에
  머문 채 끝나지 않는다. 실무자는 "느린가 보다" 하고 기다리게 된다. 과거 사건을 다시 꺼내 보는 순간
  (재상담·분쟁 재발) 바로 부딪히는 문제다.
- **근거** `src/admin/ConsultationDetail.tsx:51-68`(`watchConsultations(...)`, 마지막 인자 500 →
  `rows.find((r) => r.id === id)`), `ConsultationDetail.tsx:92-101`(못 찾으면 계속 "로드 중"),
  `src/admin/PrintLetter.tsx:10-14`(인쇄 화면도 같은 방식).
- **고칠 방향** 상세는 문서 하나만 직접 읽어 오도록 바꾸고, 없으면 "이 사건을 찾을 수 없습니다"로
  분명히 끝낸다. 지금은 "못 찾음"과 "아직 안 옴"이 같은 화면이다.

### 3. 채팅 사건은 손님이 말을 더 걸면 상태와 메모가 화면에서 사라진다 · 심각도 위험

- **어디서** 접수함·칸반·상세 전부.
- **무슨 일이** 같은 대화(sessionId)의 문서 여러 개를 1건으로 묶어 보여 주는데, **대표로 세우는 것은
  가장 최근 문서**다. 상태 변경·메모 저장은 그때의 대표 문서 하나에만 기록된다.
  그런데 채팅 중 손님이 새 전화번호를 말하거나 손해배상 협박 문구를 쓰면 **같은 대화에 새 접수 문서가
  더 만들어진다.** 그 순간 대표가 새 문서로 바뀌고, 새 문서에는 상태가 없으므로 카드가 "신규"로 되돌아가며
  어제 적어 둔 변호사 메모도 목록·칸반에서 보이지 않게 된다(옛 문서는 남아 있지만 링크가 새 문서로 간다).
  실무자 눈에는 "내가 연락 완료로 바꿨는데 왜 다시 신규지"로만 보인다.
- **근거** `src/admin/groupChatSessions.ts:17-31`(최신 문서가 대표, `chatCount`만 증가 · 상태·메모는 승계하지 않음 —
  승계하는 것은 이름·이메일·연락처·손배 플래그뿐, 같은 파일 35-38행),
  `src/admin/Kanban.tsx:59-65`·`src/admin/ConsultationDetail.tsx:103-111`(대표 id에만 기록),
  `src/components/ChatModal.tsx:671-679`(손배 감지 시 추가 접수), `ChatModal.tsx:718-726`(연락처 변경 시 추가 접수),
  `ChatModal.tsx:638-645`·`ChatModal.tsx:765-772`(연락처 제출·자동 접수 시 접수).
- **고칠 방향** 사건의 정체성을 sessionId로 잡고 상태·메모를 그 대화 단위에 저장하거나,
  묶을 때 그룹 안에 있는 상태·메모 중 가장 나중 값을 대표에 승계한다.
- (덧붙임, 추론) 의뢰인이 올린 자료는 `caseId`(문서 id)로 붙으므로, 대표가 바뀌면 상세 화면의 증거 자료
  목록도 비어 보일 수 있다 — `src/firebase.ts:825-836`, `ConsultationDetail.tsx:87-90`. 실데이터로 확인하지 않은 추측이다.

### 4. 누가 언제 상태를 바꿨는지 아무 데도 남지 않고, 되돌리기도 없다 · 심각도 위험

- **어디서** 상세 "상태 변경" 버튼 5개, 칸반 드래그·셀렉트.
- **무슨 일이** 상태를 바꾸면 문서의 `status` 한 칸만 덮어쓴다. **바꾼 사람도, 바꾼 시각도, 이전 값도 기록하지 않는다.**
  보안 규칙은 `updatedAt`·`assignedTo` 기록을 허용해 두었는데 코드가 쓰지 않는다.
  잘못 눌러 "종료"로 보낸 건을 되돌리려면 원래 무엇이었는지 기억에 의존해야 하고,
  두 사람이 쓰면 "누가 종료했어요?"에 답할 방법이 없다.
- **근거** `src/firebase.ts:494-510`(`updateConsultation` — 패치 그대로 쓰고, 승인 시각만 예외로 기록),
  `firestore.rules:32`(`updatedAt`·`assignedTo` 허용되나 미사용),
  `src/admin/ConsultationDetail.tsx:717-732`(상태 버튼), `src/admin/Kanban.tsx:59-65`.
- **고칠 방향** 최소한 `updatedAt`·`updatedBy`를 함께 쓰고, 상세 화면에 "마지막 변경 · 9/12 10:12 · 김OO"를
  한 줄 띄운다. 이력 컬렉션까지 두면 되돌리기도 만들 수 있다.

### 5. 저장이 실패해도 화면이 아무 말을 하지 않는다 · 심각도 위험

- **어디서** 상세의 상태 변경·메모 저장·초안 저장, 칸반 카드 이동.
- **무슨 일이** 저장 함수에 실패를 잡아 보여 주는 처리가 없다. 인터넷이 끊겼거나 로그인이 만료됐거나
  권한이 없으면 저장은 실패하는데, 화면에는 **"✓ 시각" 표시가 안 뜨는 것 말고 아무 변화가 없다.**
  칸반은 아예 `console.error`로 조용히 삼킨다(개발자 도구를 열어야 보인다). 실무자는 저장된 줄 알고 넘어간다.
  메모는 다시 열면 사라져 있다.
- **근거** `src/admin/ConsultationDetail.tsx:103-121`(`try { ... } finally { setSaving(false) }` — `catch` 없음,
  같은 형태가 123-134·187-198·200-217행에도 반복), `src/admin/Kanban.tsx:59-65`(`catch (e) { console.error(e) }`).
- **고칠 방향** 실패하면 화면에 붉은 한 줄로 "저장하지 못했습니다. 다시 눌러 주세요"를 띄우고,
  칸반은 카드를 원래 자리로 되돌린다.

### 6. 전화를 걸려면 손님 번호를 눈으로 읽고 직접 눌러야 한다 · 심각도 답답

  검색어로는 걸리는데(숨어서 검색만 됨) 화면에는 안 보인다. 상세로 들어가면 "연락처" 한 줄이 있지만
  그냥 글자다 — 눌러도 전화가 걸리거나 문자창이 열리지 않는다. 하루에 상담 전화를 여러 통 거는 사람에게는
  매번 "목록 → 상세 열기 → 번호 눈으로 옮겨 적기"가 된다.
- **근거** `src/admin/ConsultationsList.tsx:175-180`(userName·userEmail만 그림),

  `src/admin/ConsultationDetail.tsx:327`(`["연락처", row.contact ?? "—"]` — 평범한 글자),
  `src/admin/OrdersAdmin.tsx:131`(주문 화면의 연락처도 마찬가지).
- **고칠 방향** 목록에 연락처 칸을 넣고, 번호를 `tel:`·`sms:` 링크로 만들어 휴대폰에서 누르면 바로 걸리게 한다.
  복사 버튼 하나만 있어도 크게 낫다.

### 7. 읽음 표시도, 담당자 지정도 없다 · 심각도 답답

  누가 맡은 건인지 구분할 방법이 상태값 5개(신규·연락 완료·상담 완료·위임 체결·종료)뿐이다.
  "봤지만 아직 연락은 못 했다"를 표현할 칸이 없어서, 실무자는 결국 메모장에 따로 적게 된다.

### 8. 비밀번호를 잊으면 관리자 화면에서 할 수 있는 일이 없다 · 심각도 막힘

- **어디서** `/admin/login`.
- **무슨 일이** 로그인 화면에 "비밀번호를 잊으셨나요" 같은 링크가 없다. 코드 전체에 비밀번호 재설정 메일을
  보내는 기능이 없다. 안내 문서도 계정 만드는 법만 적고 잊었을 때는 다루지 않는다.
  즉 **Firebase 콘솔에 들어갈 수 있는 사람(개발자)에게 연락하는 것 말고는 방법이 없다.**
  그동안 접수함은 아무도 못 본다.
- 덧붙여 로그인 실패 메시지가 **Firebase의 영어 원문 그대로** 나온다.
  비밀번호를 틀리면 화면에 "⚠ Firebase: Error (auth/invalid-credential)." 같은 글자가 뜬다.
  비개발자에게는 무슨 뜻인지도, 다음에 뭘 해야 하는지도 알 수 없다.
- **근거** `src/admin/AdminLogin.tsx:44-73`(재설정 링크 없음), `AdminLogin.tsx:26-27`(`(e as Error)?.message`를 그대로 표시),
  `src/firebase.ts`에 `sendPasswordResetEmail` 사용처 없음(전체 검색 결과 0건),
  `docs/ADMIN_GUIDE.md:9-32`(계정 생성 절차만 있음).
- **고칠 방향** "비밀번호 재설정 메일 받기" 버튼을 넣고, 자주 나오는 오류는 우리말로 바꾼다
  (비밀번호가 맞지 않습니다 / 등록되지 않은 계정입니다 / 잠시 후 다시 시도해 주세요).

### 9. 되돌릴 수 없는 버튼에 확인 단계가 빠져 있다 · 심각도 위험

- **어디서** 실적 지표의 ✕ 버튼, 칸반 드래그, 상세의 상태 버튼.

  숫자가 사라진다.** 칸반은 카드를 잘못 놓는 순간 즉시 저장되며 되돌리기가 없고, 상세의 상태 버튼도 한 번에 바뀐다.
  반대로 후기 삭제·글 삭제·통보문 승인·발송 표시에는 확인 창이 있어서, 화면마다 기준이 다르다.

### 10. 결제와 접수가 한쪽으로만 이어진다 · 심각도 답답

- **어디서** 결제 주문 화면, 상담 상세.
- **무슨 일이** 주문 화면에서는 연결된 상담으로 넘어갈 수 있다. 그런데 **상담 상세에는 결제 정보가 한 글자도 없다.**

## 확신이 낮은 항목

- **증거 파일 열람이 언제까지 되는지.** 저장소 규칙은 올린 본인(uid 일치)만 읽게 되어 있고
  (`storage.rules:5-12`), 관리자 uid는 여기에 해당하지 않는다. 화면이 여는 것은 파일을 올릴 때 받아 둔
  다운로드 주소인데(`src/firebase.ts:787-807`), 이 주소에는 토큰이 붙어 있어 규칙과 무관하게 열리는 것으로 안다.
  즉 **지금은 열리지만, 토큰이 무효화되면 관리자만 못 열게 될 수 있고, 반대로 그 주소를 가진 사람은
  누구나 열 수 있다**는 뜻이다. 실제 동작은 확인하지 않았다(실데이터 접근 금지) — 추측이다.
- **3번의 "증거 자료가 안 보인다" 부분.** 대표 문서가 바뀌면 `caseId`가 달라져 파일 목록이 빈다는 것은
  코드 구조상의 추론이고, 실제 데이터로 확인하지 않았다.
- **12번의 휴대폰 화면 모양.** CSS 규칙을 읽고 판단한 것으로, 실제 기기에서 열어 보지는 않았다
  (브라우저 도구 사용 금지). 다만 "표를 위한 좁은 화면 규칙이 없다"는 사실 자체는 파일에서 확인했다.
- **8번의 오류 문구.** Firebase가 실제로 내려보내는 문자열이 `auth/invalid-credential`인지
  `auth/wrong-password`인지는 버전에 따라 다르다. 확실한 것은 **그 원문을 그대로 화면에 띄운다**는 점이다
  (`AdminLogin.tsx:26-27`).
- **1번의 "상한을 넘는다"는 전제.** 현재 접수 건수가 200건을 넘었는지는 확인하지 않았다.
  넘기 전까지는 숫자가 맞고, 넘는 순간부터 조용히 틀리기 시작한다.
